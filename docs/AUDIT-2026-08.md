# mep-toolbox 稽核報告

**稽核日期**：2026-08-18
**稽核對象**：`b70874f` 版本的 HYD-01 ~ HYD-04 四支工具、共用資產與專案結構
**驗證基準**：
- 龍慶 27MW 案送審文件 `MIC-VB-WS-CAL-0001` 水理計算書 B 版（2026/07/17）、`MIC-VB-WS-DWG-0003` 用水平衡圖 A 版（2026/07/31）
- Notion《27MW_給排水計算邏輯》
- 《建築物給水排水設備設計技術規範》、《水土保持技術規範》、《排水管理辦法》
- 水力學解析解（滿管 R = D/4、V_max/V_full = 1.140、Q_max/Q_full = 1.076 等）

**結論**：四支工具的**整體架構與資料來源標註做得比一般工程小工具好**（每個公式都寫出處、每支都有免責聲明、計算條件寫進網址），但**計算層有 4 個會直接算錯數字的缺陷**，其中 2 個量級錯誤（1000 倍、20 倍）。前端則有一個貫穿全部四支的可用性缺陷，嚴重到會讓人放棄使用。

本次已全部修正，並補上 `tests/verify.js`（81 項回歸驗證，全數通過）。

## 二、S1 — 會算錯數字

### S1-1　給水工具：摩擦損失 Ht 少算 1000 倍（量綱錯誤）

**位置**：`tools/water-supply-demand/index.html`，`calcHead()`

```js
const Ht = 0.02 * (L/Dmm) * V / (2*g);   // Dmm 是「公厘」
```

管長 `L` 的單位是公尺、管徑 `Dmm` 的單位是公厘，兩者相除得到的 L/D 比值差了 1000 倍。

**用送審計算書驗證**（L=12 m、D=150 mm、V=1.6 m/s）：

| | Ht | 說明 |
| --- | --- | --- |
| 送審書 `MIC-VB-WS-CAL-0001` 印出值 | **0.1305 m** | — |
| 正確計算 `0.02 × (12/0.15) × 1.6/(2×9.8)` | **0.13061 m** | 與送審書相符 |
| 原版工具計算 `0.02 × (12/150) × 1.6/(2×9.8)` | **0.00013 m** | 少 1000 倍 |

值得注意的是：**送審計算書本身是對的**，表格上印「D = 150.00 mm」但實際運算是用公尺代入。工具是照著表格的字面抄，所以抄錯了。

**影響**：本案因為 Ht 佔比極小（總揚程 14.96 m 中只有 0.13 m），錯誤只造成 0.3% 差異，不易察覺。但這個誤差**與管長成正比、與管徑成反比**：

| 情境 | 正確 Ht | 原版 Ht | 少算 |
| --- | --- | --- | --- |
| L=12 m, D=150 mm（本案） | 0.13 m | 0.0001 m | 0.13 m |
| L=100 m, D=50 mm | 3.27 m | 0.0033 m | **3.26 m** |
| L=300 m, D=40 mm | 12.24 m | 0.0122 m | **12.2 m** |

長管路小管徑的案子會直接少算十幾公尺揚程，泵浦選小，現場打不上去。

**修正**：`CALC.head()` 統一以公尺代入，並保留兩種模式 —— `official`（完全重現台水表格，含 V 一次方的簡化）與 `darcy`（Darcy–Weisbach 正解，V²），兩者的值同時顯示以供對照。

### S1-2　污水工具：集水坑泵浦用日平均流量選型，且預設值單位誤植

**位置**：`tools/sewage-septic-sizing/index.html`

```js
function calcPitPumpQ(dailyQm3, hours){ return dailyQm3/hours; }
// 預設 pitDailyQ = 100（標籤：本分區污水量 M³/日），pitHours = 8
// → 100/8 = 12.5 m³/h
```

**兩個錯誤疊在一起**：

1. **觀念錯誤**：「日總量 ÷ 抽水時數」得到的是平均流量。泵浦必須吃得下**尖峰入流**，否則集水坑會持續累積並溢流。生活污水有明顯的人為作息尖峰（Harmon 式在 75 人時給出 PF ≈ 4.28），製程廢水則要看排放是連續還是間歇。

2. **單位誤植**：預設值 `100` 是從圖說的泵浦規格表抄來的 —— 圖說上「放流採樣井 #AA　Q=100」的單位是 **m³/hr**（泵浦流量），卻被填進標籤為「M³/**日**」的欄位。

**量級對照**：

| | 流量 |
| --- | --- |
| 全案污水總量（用水平衡圖） | 116.4 M³/**日** |
| 日平均時流量 | 4.85 m³/h |
| 原版工具算出的「泵浦流量」 | 12.5 m³/h |
| 圖說實際選用的泵浦 | **100 m³/h** |

原版與實際選型差 8 倍。而合理的解釋是：冷卻水塔 blowdown 108.5 M³/日若**集中在約 1 小時內排放**，瞬時流量就是 108 m³/h —— 這正是 100 m³/h 泵浦的來歷。

**修正**：新增「④ 尖峰排放流量」步驟，生活污水套 Harmon 尖峰係數（可手動覆寫、可設上限），製程廢水依「連續／間歇」模式與實際排放時數計算。並在頁面上直接寫出這個 24 倍的差異提醒使用者去問空調團隊。

### S1-3　雨水工具：降雨強度與集流時間脫鉤

**位置**：`tools/rational-method/index.html`

原版把 IDF 公式裡的延時 `t` 做成一個獨立的輸入欄位（預設 20 分），與集水區的實際條件毫無關聯，而且**手動輸入 I 的模式下根本沒有 t 的概念**。

合理化公式的成立前提是「**降雨延時 = 集流時間 t_c**」—— 只有當降雨持續到整個集水區都對出口有貢獻時，才會出現尖峰流量。t 隨便填，算出來的 I 就是錯的，Q 也跟著錯。而 I 對 t 相當敏感（水保公式在 t 從 20 分改到 60 分時，I 大約掉 40%）。

原版也沒有任何計算 t_c 的工具，使用者只能猜。

**修正**：新增「② 集流時間 t_c」步驟，提供四種算法：
- 水保技術規範 §19：t_c = 漫地流 t₁（l/v，v 取 0.3~0.6 m/s、l ≤ 100 m）＋ 芮哈公式 t₂ = L/W，W = 72(H/L)^0.6
- 都市式：入流時間（5~10 分）＋ 管渠流下時間 L/v
- Kirpich（僅供對照，並註明其率定條件為美國田納西州小型農地集水區，用於都市化基地會低估 t_c）
- 手動輸入

I 的計算一律綁定 t_c，並在 t_c < 10 分時警告。

### S1-4　Manning 工具：求解充滿度時會誤判「無解」

**位置**：`tools/manning-calculator/index.html`，`computeAll()` 的 `target === 'r'` 分支

```js
let flo = valAt(lo)-targetVal, fhi = valAt(hi)-targetVal;
if((flo>0 && fhi>0) || (flo<0 && fhi<0)){ out.valid=false; }   // ← 誤判
```

二分法假設函數在區間內單調。但圓管部分充滿流**不是單調的**：

- 流速在 **r ≈ 81.3%** 達到最大，`V_max / V_full = 1.140`
- 流量在 **r ≈ 93.8%** 達到最大，`Q_max / Q_full = 1.076`

造成兩個具體錯誤：

1. **有解卻回報無解**：目標 Q 落在 `Q_full` 與 `Q_max` 之間時（實際上有兩個解），區間兩端的函數值同號，程式直接判定無解。這個區間佔滿管流量的 7.6%，在管徑選型時很容易踩到。
2. **有兩個解時只給一個**，且不告訴使用者另一個存在。

**修正**：改用「掃描 2000 點找符號變化 → 對每個變化區間各做一次二分」，找出全部根。UI 顯示較小的根（正常設計解），並在有多重根時說明原因與另一個根的位置。同時新增「滿管特性」面板，直接把 V_full / Q_full / V_max / Q_max 及其發生位置列出來。真正無解時（目標值超過極大值），錯誤訊息會告訴使用者極大值是多少、發生在哪個充滿度。

## 五、S4 — UI/UX 與前端實作

### S4-1　（最嚴重）打字打到一半焦點被吃掉 —— 四支工具全中

四支工具的表格輸入都是這個模式：

```js
inp.addEventListener('input', e=>{
  state.rows[i][f] = parseFloat(e.target.value)||0;
  renderRows();          // ← innerHTML 重建整個 tbody
  computeAndRender();
});
```

每按一個鍵就把整個 `<tbody>` 用 `innerHTML` 砍掉重建。後果：

1. **輸入框被銷毀，焦點消失**，游標跳走，必須重新點一次才能繼續打。
2. **小數點打不出來**。想輸入 `0.85`：打到 `0.` 時 `parseFloat("0.")` 回傳 `0`，重建的 input 直接顯示 `0`，`.85` 永遠打不進去。使用者只能用貼上或方向鍵。
3. Manning 工具更嚴重 —— 連 D / S / r 這些非表格欄位也是每個 keystroke 就 `innerHTML = ''` 重建，還用 `setTimeout(...,0)` 補綁事件。

這不是美觀問題，是**工具能不能用**的問題。

**修正**：新增共用的 `bindInput()`：輸入時只寫 state 與重算，**絕不重建輸入元素**；只更新計算欄位的 `textContent`。列的建立與刪除才重建 DOM。回填數值時跳過 `document.activeElement`，避免覆蓋正在輸入的內容。空值／NaN 的正規化延後到 `blur` 才做。

## 七、建議的下一步（本次未做）

1. **FIR-01 消防水源容量計算工具**。依《各類場所消防安全設備設置標準》計算室內外消防栓、自動撒水、水霧等系統的水源容量與加壓送水裝置。資料中心另有氣體滅火系統（本案 `MIC-VB-FP-CAL-0001` 消防氣體計算書）與 VESDA，值得獨立一支。消防水池與生活水池**容量須各自滿足、不可混算**，這正是給水工具目前只用一句註腳帶過的部分。

2. **工具之間的資料串接**。目前 HYD-02 算出的 Q、HYD-04 算出的尖峰流量，都要人工抄到 HYD-01 去核管徑。既然狀態已經在網址裡，可以做成「帶著這個 Q 去 Manning 工具」的連結。

3. **分區計算**。本案給水採分區供水（辦公區 50mm／警衛室 20mm／空調用水 50mm 各自獨立泵組），但 HYD-03 一次只能算一個分區的總量。工具已加警語，但真正好用的做法是支援多分區並列。

4. **通氣管系統**。DFU 只決定管徑，不保證系統能用 —— 存水彎沒有對應通氣，封水會被抽乾、臭氣竄回室內。這塊目前四支工具都沒碰。

5. **當地 IDF 係數建檔**。高雄小港的實測 IDF 曲線係數若能拿到，比水保通式準得多，值得建成一個可選的測站清單。
